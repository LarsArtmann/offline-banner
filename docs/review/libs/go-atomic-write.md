## 1. What the library is

Crash-safe, race-free file writes for Go. Its README identifies the three failure modes of `os.WriteFile` — concurrent overwrite (TOCTOU), half-written files on crash, interleaved bytes from concurrent writers — and eliminates all three with one pipeline: fingerprint read (xxhash64) → unique temp file → fsync → flock + re-verify → single `rename(2)` → fsync directory. Two deliberate dependencies (xxhash, gofrs/flock), cross-platform down to Windows `MoveFileEx` retry semantics.

Atomicity was never the problem there — ordering was.

## 4. Should offline-banner adopt it?

**SHOULD NOT adopt the library — but this is the one report in the fleet run where the library's contract deserves line-by-line comparison, because offline-banner independently implemented its core.**

**Does the contract validate the sh recipe? Yes, at its core.** The library's "How it works" is a 6-step contract: unique temp → fsync → lock+verify → single `rename(2)` → dir fsync. The sh recipe implements steps 1 (weakened: fixed name) and 4 (single `rename(2)` via same-directory `mv -f`) and skips 2, 3, and the dir fsync. The empty-file tear was a _plain truncate-write_ (`> state`) — precisely the row the library's comparison table labels "DIY write + rename: crash-durable **Partial**", one row above the fully-safe column. The library's doctrine is the _reference specification_ of the fix offline-banner rediscovered empirically through CI; its README could be cited today as the spec for why line 594 looks the way it does.

**Could its doctrine have prevented the tear? Yes — and did, retroactively.** The tear mechanism (reader opens the file during truncate-write) is exactly failure mode #2 in the README ("a crash mid-write leaves a half-written file" — with readers substituted for crash). Staging to a temp and renaming closes it. The recipe already does this, so the doctrine's value now is preventive: any future writer added to this repo must follow the same stage+rename rule, and the library's docs are the citable standard.

**Where the recipe falls short of the contract, and whether it matters:**

1. **Fixed temp name vs unique suffix — IMPLEMENTED 2026-11-18.** `"$1.tmp"` was safe only while `emitState()` was the sole writer. The 2026-11-18 orphan-`mv` incident proved spawned writers can overlap across instance lifetimes in practice (caught by test draining, not by the recipe). The library's unique-suffix rule (`"$1.$$.tmp"` in sh — pid is enough here) is now IN the recipe, live-proven through a sandboxed transient. The last assumption is removed.
2. **No fsync before rename.** POSIX sh cannot fsync a single file. On a power loss between `>` and the writeback, the renamed target can be short or zero-length on filesystems without rename-flush heuristics; ext4's `auto_da_alloc` specifically detects rename-over-existing and flushes, so on NixOS's default ext4 the practical window is small. Decisive for the verdict: the data is _ephemeral runtime state_ whose consumers fail closed — a zero-length or stale `updatedAt` reads as "unit dead", which is the correct presentation anyway. The gap is real on paper and trivial by design.
3. **No TOCTOU machinery.** One writer, read-only consumers: the fingerprint/flock half of the library has no race to catch here. Note the library itself documents why its zero-fingerprint first-write path checks existence _before_ flock (flock's `O_CREATE` would false-positive) — nice contract subtlety, irrelevant to a single-writer sh recipe.
4. **`WriteIfChanged` is an anti-feature for a heartbeat.** The library markets no-mtime-bump as a benefit for file-watcher users; the state file's whole job is to _change_ on every probe so staleness proves death. A doctrine collision worth remembering in reverse: dedup-on-write and liveness-heartbeat are opposing requirements on the same file-writing primitive.

**Honest bottom line:** structurally NOT-APPLICABLE (Go library, zero Go runtime, and the recipe's needs are 12 lines of sh systemd already scaffolds). Conceptually, this library is the consumer's closest relative in the fleet: same failure taxonomy, same fix, two independent discoveries — one via CI evidence, one via design.

## 5. Fleet perspective

This is the fleet run's proof that a justified NOT-APPLICABLE can still transfer value: the transferable artifact is not code but the _contract_ — stage to a uniquely-named temp, one rename, say what you do and do not guarantee. Three concrete non-Go carries: (1) the recipe should adopt the unique-temp-name rule (`"$1.$$.tmp"`), because the orphan-mv incident shows single-writer assumptions rot; (2) the module.nix comment citing the CI-proven tear should ideally also cite the guarantee boundary the 2026-11-18 drain incident exposed — atomic-per-write, not ordered-across-writes — since that distinction is exactly what a future contributor will assume wrongly; (3) go-atomic-write's README comparison table ("naive write+rename: crash-durable Partial") is a ready-made citation for any fleet repo documenting why it renames instead of truncating. None of this adds a dependency to offline-banner; all of it makes its hand-rolled recipe contract-conscious.

## 6. If the flip trigger fires

1. **A second sh writer joins the state file** (debug tool, migration script): do NOT reach for Go — the recipe already stages pid-uniquely (`"$1.$$.tmp"`, applied 2026-11-18), so serialize writers next, citing go-atomic-write's stage_collision doctrine. The library becomes attractive only if the writers get read-modify-write semantics.
2. **Real Go code appears that writes shared/read files** (companion CLI, exporter): adopt `atomicwrite.WriteVerified` with `FingerprintFile` for read-modify-write paths and plain `Write` for first-writes; keep `ErrConcurrentModification` handling at the call site (re-read + retry) rather than wrapping it.
3. **The state file gains durability requirements** (survives reboot, feeds a ledger): that is the moment the sh recipe's missing fsync stops being harmless — port the writer into Go (`WriteFunc` streaming if the document grows) or add a tiny fsync helper, because "fail closed" stops covering data you promised to keep.
4. **Never** swap the heartbeat file to a `WriteIfChanged`-style dedup — content-diff suppression silently kills the liveness signal the whole observability story rests on.
